Layers of visibility, from inside a call out to your dashboards and billing.

## 1. Per-turn timing & token hooks

The real per-turn timing and token numbers arrive on two hooks. Register them
on the session. Both pass keyword arguments, so end each signature with `**_`
to stay compatible when fields are added:

```python
@ctx.session.on("llm_call")
async def _(turn_id, node_id, model, call_type, latency_ms,
            tokens_in, tokens_out, prompt_messages, response_json, edge_id,
            cached=0, cache_write=0, estimated=False, **_) -> None:
    # fired once per LLM call within a turn (superdialog brains only)
    push_to_grafana({"model": model, "latency_ms": latency_ms,
                     "tokens_in": tokens_in, "tokens_out": tokens_out})

@ctx.session.on("turn_complete")
async def _(turn_id, ttfa_ms, asr_ms, llm_ttft_ms, tts_ttfb_ms, stt_ms, tts_ms,
            from_node, to_node, llm_call_count, llm_total_ms,
            user_text, agent_text, **_) -> None:
    # fired when the reply ends (only ttfa_ms set), and again for each
    # timing report from the media worker (stage latencies set)
    print(turn_id, ttfa_ms, llm_total_ms)
```

<Note>
`llm_call` and `turn_complete` carry the actual per-turn latency and token data.
`turn_complete` can fire twice for one `turn_id` - dedupe on `turn_id` before
you aggregate. The `CallMetrics` snapshot below (`metrics.live()`) only
populates if you feed it from these hooks - see the caveat in Layer 2.
</Note>

## 2. Live per-call snapshot (opt-in)

Inside (or after) `session.run()`, take a `CallMetrics` snapshot:

```python
m = ctx.session.metrics.live()

m.turns           # int: dialog turns
m.duration_s      # float
m.stt_p95_ms      # int: P95 speech-to-text latency
m.llm_p95_ms      # int: P95 brain latency
m.tts_p95_ms      # int: P95 synthesis latency
m.cost.total      # float
m.tokens.input    # int
m.tokens.output   # int
m.active_llm      # str: model used on the last turn
```

<Warning>
The latency/cost/token fields populate **only if you call
`metrics.record_turn(...)` yourself** - typically from the `turn_complete` hook
above. The SDK does not auto-fill them, so out of the box only `duration_s` is
meaningful. For real numbers, use the per-turn hooks (Layer 1).
</Warning>

## 3. Usage & billing ledger

The SDK buffers per-session LLM usage and flushes it to the cloud billing ledger
on `call_end`. It is **best-effort**: a no-op when `UNPOD_USAGE_INGEST_URL` is
unset, and never blocks or fails the call.

```bash
UNPOD_USAGE_INGEST_URL="https://..."          # ingest base URL; enables the ledger
UNPOD_USAGE_INGEST_TOKEN="..."                # optional auth
```

Counters posted per session:

| Counter | Meaning |
|---|---|
| `llm_prompt_tokens` | Prompt tokens |
| `llm_completion_tokens` | Completion tokens |
| `llm_cached_tokens` | Prompt-cache **read** tokens |
| `llm_cache_write_tokens` | Prompt-cache **write** tokens |
| `llm_provider` / `llm_model` | Provider + model attribution |

Prompt-cache read/write tokens are forwarded so cached turns are billed at the
correct (lower) rate.

## 4. Langfuse tracing

Install the extra, then set the Langfuse keys. The SDK emits per-turn spans
plus a generation span per LLM call (with token usage):

```bash
pip install "unpod[observability]"      # installs langfuse

LANGFUSE_SECRET_KEY="sk-lf-..."
LANGFUSE_PUBLIC_KEY="pk-lf-..."
LANGFUSE_HOST="https://cloud.langfuse.com"   # only for a non-default host
```

Tracing turns on only when `LANGFUSE_SECRET_KEY` is set. Without the extra, or
if the Langfuse client cannot start, the SDK skips tracing silently - hooks
still fire.

## 5. Runner pool stats

```python
s = runner.stats()        # RunnerStats snapshot

s.in_flight               # current active calls
s.queued                  # always 0 in SDK 0.7.0
s.capacity                # your max_sessions setting
s.completed_last_hour     # since the runner started
s.failed_last_hour        # since the runner started
s.mean_call_duration_s
```

Poll this on a timer for liveness dashboards - see
[AgentRunner & Sessions](/agent-sdk/agent-runner#running-in-production).

## 6. Post-call timing

After the call, `calls.get(call_id)` returns the call's latency and timing
data:

| Field | Description |
|---|---|
| `latency_summary` | Per-call latency roll-up (`dict`) |
| `latency_metrics` | The per-turn latency rows behind it (`list[dict]`, detail reads) |
| `call_timings` | Property: `call_dialed_at`, `call_connected_at`, `call_ended_at`, `ring_duration_seconds`, `talk_duration_seconds`; `{}` when not recorded |

These are plain dicts; their keys are not typed by the SDK. For stage
latencies you can act on during the call, record the `turn_complete` hook
(Layer 1).

<Tip>
High `llm_ttft_ms` with healthy `asr_ms`/`tts_ttfb_ms` means the latency is in
YOUR brain - usually a `stream()` that is not actually streaming. See
[Streaming is the hot path](/agent-sdk/bring-your-agent#streaming-is-the-hot-path).
</Tip>
