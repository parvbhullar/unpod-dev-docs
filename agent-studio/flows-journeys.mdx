Flows & Journeys are durable communication workflows. A **flow** is the plan: a
versioned sequence of steps - messages, agent steps, calls, and human approval. A **journey** is one entity's traversal of one flow. When a journey
starts, the plan is copied for that entity, so editing a flow never mutates
journeys already in flight.

The point of the split is time. A single call lasts minutes; a real outreach
sequence spans days. Journeys can pause for a human to approve the next move.
When the person replies on any channel, the inbound reply reaches the running
journey as a signal. Your agent never calls someone who already answered
yesterday's email.

<Note>
Journey flows are campaign step sequences, a different concept from
SuperDialog's conversation-graph flows, which drive turns inside a single
conversation. See [SuperDialog](/superdialog/introduction) for that engine.
</Note>

## The primitives

| Primitive | What it is | Where it lives today |
|---|---|---|
| Flows | The versioned step sequence - the plan | Python SDK: `unpod.flows` builder, `client.flows` (create, validate, activate, pause, archive, versions) |
| Steps | One unit in the sequence | SDK builder: message and agent steps on a channel (`MessageStep`, `AgentStep`). Call steps run as tasks - [Make Call task](/api/execution/task-make-call-overview) |
| Journeys | One entity's traversal of one flow, with the plan copied per entity | `client.journeys` (start, get, list, cancel, resume); call steps surface as [runs](/api/execution/runs-overview) |
| Signals | External input a running journey reacts to: an inbound reply, a human approval, a cancel | `client.journeys.send_event`, `approve`, `cancel` |

Tasks are the unit of work inside Execution. A call step does not reimplement
calling - it dispatches a task to the
[Calling Engine](/telephony/concepts/calling-engine) unchanged, the same
[Make Call task](/api/execution/task-make-call-overview) you can dispatch
directly today. The journey adds the before and after: when to place the call,
and what its outcome means for the next step.

## Build a flow in Python

The `unpod` Python SDK (0.7.0) ships a flow builder. `Flow(...).to_definition()`
is the JSON body `client.flows.create(space, flow)` sends:

```python
from unpod.flows import AgentStep, Flow, MessageStep

flow = Flow(
    name="Demo follow-up",
    goal="Book a 20-minute product demo.",      # the agent's objective
    steps=[
        MessageStep(account_id="acc_123", action="email", connector="gmail",
                    subject="Quick question", body="Would a short demo next week help?"),
        AgentStep(account_id="acc_123", action="email", connector="gmail"),
    ],
)
print(flow.to_definition())
```

In a real flow, pass `channel=` (one of `client.flows.channels.list(space)`)
instead of the account fields. Then:

- `client.flows.create(space, flow)` saves it, and `client.flows.activate(flow)`
  switches it on.
- `client.journeys.start(flow_id, participant_id=..., contact={...})` starts a
  journey per contact; `get`, `list`, `cancel`, and `resume` manage it.
- `client.journeys.send_event(journey_id, type=...)` signals a running journey,
  such as a reply.
- `client.journeys.set_approval(space_id, level)` sets how much the space's
  agent may do on its own: `autonomous`, `human_review` (the default), `shadow`,
  or `blocked`. Under `human_review`, `client.journeys.draft(journey_id)` shows the
  held message and `client.journeys.approve(journey_id)` sends it.

<Note>
Channel lookup and space resolution need proxy-mode auth: a signed-in user's JWT
through `JWTAuth(token, org_handle=...)`. The platform token alone is refused
for those calls.
</Note>

## On the spine

A journey is attached to one entity. It reads the entity's
[context](/intelligence/memory), dispatches interactions through the Talk layer
as tasks, and consumes the structured [outcome](/intelligence/outcomes) each
interaction produces. Every journey transition - started, step completed,
signaled, exited - emits an [event](/core-engine/events), so the rest of your system can
react without polling.

## What stays hidden

The workflow engine underneath - Temporal-style durable execution, timer
persistence, retry semantics, replay - is deliberately not exposed. You define
flows in terms of steps and signals; how a journey survives a restart
or holds a three-day timer is Unpod's problem, not a queue you operate.

## Status

The Python SDK builds and runs channel flows today: message and agent steps,
journeys you can start, signal, and cancel, and space-level agent approval
(`human_review` drafts you approve). Call steps are real too: dispatch them as
[tasks](/api/execution/task-make-call-overview) and inspect
[runs](/api/execution/runs-overview).
