Unpod signs the requests it sends your app with one org-level key, the **webhook secret**.
It's the same key for status callbacks, recording events, answer-URL requests and audio
streams, with no secret per number or per call. Read it with `reveal()` (org admin) and store
it as `UNPOD_WEBHOOK_SECRET`. Then verify each request with `parse_call_event`.

| Event type | Goes to |
| --- | --- |
| Call events (leg lifecycle, audio, DTMF) | `status_callback_url` |
| Recording events | `recording_callback_url` |
| Inbound events | Your answer URL |
| [Stream events](#stream-events) | The stream's `statusCallbackUrl` |

## Which requests are signed

| Request | Signed? |
| --- | --- |
| Inbound answer-URL POST (`StartApp`, `Hangup`, `RecordStop`) | Yes |
| Outbound answer-URL POST (`answer_url` on `create`) | Yes |
| `<GetDigits>` / `<GetInput>` and `<Record recordSession>` `action` requests (POST) | Yes |
| Status callbacks, including `Incoming` | Yes |
| Recording events (`MPCRecordingCompleted`, `ParticipantRecording...`) | Yes |
| [Stream events](#stream-events) | Yes: a POST over its body, a GET over its full query string |
| Any GET answer-URL request | No: there's no body to sign |
| The audio-stream WebSocket connection | Yes, with a different header, `X-Unpod-Signature`. See [Audio Streaming](/telephony/apis/audio-streaming#verify-the-stream-signature) |

"Yes" applies once your org has a secret: until then every request goes out unsigned, so
create it ([Rotate the webhook secret](/telephony/concepts/security-and-compliance#rotate-the-webhook-secret)) before you point anything at a server that verifies. `parse_call_event` rejects
an unsigned request. Parse a GET request with `verify=False` and trust only what the API
returns.

## Get the secret

```python
from unpod import Client

with Client() as client:
    s = client.telephony.webhook_secret.reveal()  # org admin
    print(s.version, s.secret)  # full secret: store as UNPOD_WEBHOOK_SECRET

    print(client.telephony.webhook_secret.get().secret)  # masked, e.g. '****ab12'
```

`reveal()` and `get()` only read the secret; nothing changes for servers already verifying
with it. To create the first secret or replace a leaked one, see
[Rotate the webhook secret](/telephony/concepts/security-and-compliance#rotate-the-webhook-secret). For the cURL call, see
[The webhook secret](/telephony/apis/incoming-calls#the-webhook-secret).

## Verify and parse

```python
import os

from fastapi import FastAPI, HTTPException, Request
from unpod.telephony import WebhookSignatureError, parse_call_event

SECRET = os.environ["UNPOD_WEBHOOK_SECRET"]
app = FastAPI()
seen: set[str] = set()


@app.post("/call-status")
async def call_status(request: Request):
    body = await request.body()
    try:
        ev = parse_call_event(body, request.headers, secret=SECRET)
    except WebhookSignatureError:
        raise HTTPException(401)  # unsigned, wrong secret, or older than 300 s

    if ev.event_id:  # the same event can arrive more than once
        if ev.event_id in seen:
            return {"ok": True}
        seen.add(ev.event_id)

    if ev.event == "Answered":
        print(ev.call_id, ev.leg_id, ev.role, "answered")
    elif ev.event == "Hangup":
        print(ev.hangup_cause, ev.sip_code, ev.duration)
    return {"ok": True}  # any 2xx acknowledges
```

Rules:

- Pass the **raw body** exactly as received. Re-encoding it breaks the signature.
- `Content-Type` decides form or JSON; `parse_call_event` reads both.
- The same event can arrive more than once (see
  [Delivery and retries](#delivery-and-retries)). De-duplicate on `ev.event_id`, and pass
  an `idempotency_key` when an event triggers `add_participant`.
- Return 2xx for events you don't need, so they aren't retried.
- `tolerance` (default 300 s) rejects replays. `verify=False` skips the check: use it only
  for local tests and for the [unsigned requests](#which-requests-are-signed).

The signature header is
`X-Webhook-Signature: t=<unix ts>,v1=<hex HMAC-SHA256(secret, "<ts>.<raw body>")>`.

## Delivery and retries

Unpod POSTs each status callback and recording event and waits up to 10 s for a 2xx. Any
other status, a timeout or a connection error is a failure, and Unpod tries again: 4
attempts in all, about 1 s, 5 s and 30 s apart (each wait varies by up to 25%, so 27-45 s
of waiting in all). Each attempt can take up to 10 s, so the window from the first attempt
to the last is roughly 27-75 s. Then the event is marked failed and never sent again.

- Events for one leg arrive in order (`ev.sequence`). While one is being retried, that
  leg's later events wait behind it; other legs aren't held up.
- An event queued before the secret is [rotated](/telephony/concepts/security-and-compliance#rotate-the-webhook-secret) is retried signed with the old key,
  so a server that already has the new key rejects it.
- Return 2xx fast and do slow work afterwards. A reply slower than 10 s is a failure.
- Make handlers idempotent: the same `ev.event_id` can arrive twice, for example when
  your 2xx is lost.
- A lost `Answered` or `Hangup` can leave someone on the line. As a backstop, sweep your
  active calls with [`calls.list()`](/telephony/apis/call-control#inspect-and-end-calls)
  every few minutes, walking every page until one comes back empty, and end any that
  should be over.
- Answer-URL requests aren't retried: a failed `StartApp` applies the
  [fallback](/telephony/apis/answer-url#timeouts-and-fallback), and `Hangup` and
  `RecordStop` are sent once.

## Events

| `ev.event` | When |
| --- | --- |
| `Incoming` | An inbound call arrived. Sent to the number's `status_callback_url`, first on the caller's leg |
| `Initiated`, `Ringing`, `Answered`, `Hangup` | Leg lifecycle. Each leg gets its own `Hangup`. `Ringing` isn't always sent: on many mobile networks a leg goes straight from `Initiated` to `Answered` |
| `PlayStarted`, `PlayStopped` | Audio or speech on a leg (`ev.play_id`) |
| `DTMF` | A key was pressed (`ev.digit`) |
| `Hold`, `Unhold` | Hold changes on an answered leg |
| `MPCRecordingCompleted` | Recording ready, sent only to `recording_callback_url`. No `metadata`; `ev.recording_url` is a path inside Unpod, so fetch it with `get_recording(ev.call_id)`. See [Recording](/telephony/apis/recording#recording-events) |
| `ParticipantRecordingInitiated`, `ParticipantRecordingCompleted` | Per leg, only with `record_participant_track=True`. Sent together after the call, with the leg's channel in `ev.metadata["channel"]` (`1` left, `2` right). Only `Completed` carries the recording, in `ev.metadata["recording_url"]` |
| `StartApp`, `Hangup`, `RecordStop` | Answer-URL events, with `ev.call_status`. See [Answer URL & XML](/telephony/apis/answer-url#what-unpod-sends) |
| `started`, `stopped`, `failed`, `degraded` | Audio-stream lifecycle, sent only to the stream's `statusCallbackUrl`. See [Stream events](#stream-events) |

## `CallEvent` fields

Form wire names are below; with `status_callback_format="json"` the same fields come in
snake_case (`call_id`, `leg_id`, ...).

| Field | Wire name | Notes |
| --- | --- | --- |
| `event` | `EventName` / `Event` | One of the [events](#events) above |
| `call_id` | `MPCUUID` | The same on every event of a call, across all its legs. Not sent on [stream events](#stream-events), so `ev.call_id` is `None` there |
| `leg_id` | `CallUUID` | Differs per leg |
| `role`, `direction`, `call_status` | `Role`, `Direction`, `CallStatus` | `role` is the label you set on the leg |
| `from_`, `to` | `From`, `To` | Only on `Incoming` and answer-URL events. `None` on leg events, so outbound status callbacks never have them: put your own ids in `metadata`. On inbound calls `From` can be in national format (`09000000002`) while `To` is E.164 |
| `start_time`, `answer_time`, `end_time`, `timestamp` | `StartTime`, ... | Unix seconds |
| `initiation_time`, `hangup_time`, `duration` | `InitiationTime`, `HangupTime`, `Duration` | `duration` is answered seconds, `0` if never answered |
| `hangup_cause`, `hangup_by`, `sip_code` | `HangupCause` / `PlivoHangupCause`, `HangupBy`, `SipCode` | `Hangup` only. See [Hangup causes](#hangup-causes) |
| `digit`, `play_id` | `Digit`, `PlayId` | |
| `sequence` | `Sequence` | Per leg, from 1 |
| `event_id` | `EventId` | Stable across retries: de-duplicate on it |
| `recording_url`, `recording_duration`, `record_file` | `RecordingURL` / `RecordUrl`, `RecordingDuration`, `RecordFile` | Recording and `RecordStop` events |
| `metadata` | `Metadata` | The `metadata` you set on `create` or `add_participant`, echoed on the events of that leg (an `add_participant` leg without its own falls back to the call's). Inbound calls carry metadata only on `Incoming` |
| `raw` | | Every field exactly as received |

<Warning>
`ev.metadata` works only with the default form format. With
`status_callback_format="json"`, `parse_call_event` (SDK 0.7.0 and earlier) leaves it empty because it
reads only the form field `Metadata`. Keep the form format, or read
`ev.raw["metadata"]`.
</Warning>

## Stream events

A stream you start with `<Stream>` or `start_stream` sends its lifecycle to its own
`statusCallbackUrl` (`status_callback_url` on `start_stream`), signed like every other
callback. Without that URL there are no stream callbacks: they don't fall back to the
answer URL or the call's `status_callback_url`. See
[Audio Streaming](/telephony/apis/audio-streaming#status-callbacks).

```python
from unpod.telephony import STREAM_EVENTS

if ev.event in STREAM_EVENTS:  # ev from parse_call_event, as above
    print(ev.stream_id, ev.event, ev.stream_reason, ev.error)
```

| `ev.event` | When | `ev.stream_reason` (`StatusReason`) |
| --- | --- | --- |
| `started` | The stream started | - |
| `stopped` | The stream ended. Also carries `Duration` | `completed`, `api_request`, `stream_timeout`, `call_hangup` |
| `failed` | The stream couldn't start or broke off. Also carries `Duration` and `Error` (`ev.error`) | `start_failed`, `connection_failed`, `authentication_failed`, `connection_dropped`, `slow_connection`, `message_too_large` |
| `degraded` | A warning: your WebSocket server is reading audio too slowly (12, 24 and 36 s without a successful write; the stream fails at 40 s), or the playback queue (about 40 s) is full. The stream keeps running | `slow_connection_30`, `slow_connection_60`, `slow_connection_90`, `buffer_overflow` |

Every stream event also carries:

| Field | Wire name | Notes |
| --- | --- | --- |
| `stream_id` | `StreamID` | Always set on a stream event |
| `leg_id` | `CallUUID` | `<call id>-caller` or `<call id>-callee` |
| `event_time` | `Timestamp` | ISO 8601, for example `2024-01-15T10:30:00Z` (not Unix seconds) |
| `from_`, `to`, `direction` | `From`, `To`, `Direction` | |
| `service_url` | `ServiceURL` | The stream's WebSocket URL, query string removed |
| `extra_headers` | `ExtraHeaders` | The stream's `extraHeaders` |

## Hangup causes

| `ev.hangup_cause` | `ev.sip_code` | Meaning |
| --- | --- | --- |
| `"Normal Hangup"` | `None` | The leg was answered. `ev.hangup_by` says who hung up: the person on that leg (`callee`), or Unpod (`system`), for example after `hangup()` or when the first person left a two-person call |
| `"Busy Line"` | 486 or 600 | Busy. End the call or retry later |
| `"No Answer"` | 408 or 480 | The far end reported no answer. Treat like a ring timeout. A 408 with `Duration` 0 can also mean the call never reached the phone: [Call Logs](/telephony/calls/call-logs) then show `failure_source: sbc` and `sip_cause: Request Timeout` |
| `"Ring Timeout Reached"` | 487, or `None` | The leg rang for `ring_timeout` seconds without an answer |
| `"Rejected"` | 603, or `None` | Declined, or the callee ended the leg before answering |
| `"Cancelled"` | 487, or `None` | The caller (or your app) ended the leg before it was answered |
| `"Invalid Destination Address"` | 404, 484 or 604 | The number doesn't exist or is incomplete |
| `"Forbidden"` | 401, 403 or 407 | The carrier refused the call |
| `"Service Unavailable"` | Any 5xx | The call couldn't be placed. At your org's cap, `create` and `add_participant` normally return `429` right away; a 503 hangup means a burst passed that check and hit the cap while dialing (see [Call Blasting](/telephony/apis/call-blasting#3-track-results)) |
| `"End Of XML Instructions"` | `None` | Your [answer-URL reply](/telephony/apis/answer-url#reply-with-xml-or-json) ran out of verbs and Unpod hung up (`ev.hangup_by` is `system`). An explicit `<Hangup>` doesn't report it |
| `"Unknown"` | Any other code, or `None` | Anything else |

The strings are exact. Match on `ev.hangup_cause` first. `ev.sip_code` is always set for
`Busy Line`, `No Answer`, `Invalid Destination Address`, `Forbidden` and
`Service Unavailable`. It's `None` on an answered leg, and can be `None` for `Rejected`,
`Cancelled`, `Unknown` and `Ring Timeout Reached`. A ring timeout also reports the 487
from cancelling the ringing leg, so 487 alone doesn't mean a cancel.
